# חוזה כתיבת בדיקות — קרא לפני שאתה כותב או משנה בדיקה

> **למה זה קיים:** קשת "הדף החם" (2026-07-23/24) הורידה את הסוויטה מ-**3+ דקות ל-~54 שניות** ופענחה
> את שורש הפלייקיות בווינדוס (serialization של ה-loopback). כל בדיקה שנכתבת מחוץ לחוזה הזה מאבדת את
> שתי התכונות — היא איטית **וגם** פלייקית, והפלייקיות מתפרשת בטעות כבאג מוצר. סוכן שכותב בדיקה בסגנון
> הישן חייב להיעצר ולכתוב מחדש. (‏L18, ‏§11a במסמך המשמעת.)

## 1. הכלל היחיד שאסור לשבור

**כל בדיקה משתמשת ב-`test` ו-`seedApp` מתוך `./_fixtures` — לעולם לא ב-`test` של Playwright ישירות.**

```ts
import { test, expect, seedApp } from './_fixtures';

test('...', async ({ page }) => {
  await seedApp(page, { 'mk-lang': 'fr' });   // מצב ההתחלה = localStorage בלבד
  // ...
});
```

- `page` הוא **כבר** הדף החם (מ-2026-07-23 הוא alias ל-`warm`): context אחד ודף אחד לכל worker,
  עם `goto` קר **אחד** בלבד. ‏`seedApp` מבצע reset פר-בדיקה (ניקוי אחסון → זריעת מפתחות → reload).
- **`addInitScript` אסור בדף החם** — הוא מצטבר לכל הבדיקות הבאות. הפיקסצ'ר יזרוק חריגה מפורשת.
  זריעת מצב נעשית **רק** דרך `seedApp(page, kv)`.
- ‏`goto('/index.html')` ידני מיותר: `seedApp` עושה זאת כשצריך. אל תנווט "ליתר ביטחון".

## 2. מתי מותר לצאת מהדף החם — `isolatedPage`

פתח-מילוט לבדיקות שדורשות בידוד אמיתי פר-בדיקה: שעון מזויף (`clock`), פרויקט ה-service-worker,
כל `test.use` שמשנה אפשרויות context, וכל מקרה שבו באמת נדרש `addInitScript`.

```ts
test('...', async ({ isolatedPage }) => { /* context משלו, addInitScript מותר */ });
```

**עלות:** ‏context+goto מלאים — איטי. השתמש רק כשיש סיבה, ואמור אותה בתגובה בקוד.

## 3. תרופת ה-loopback — ולמה אסור "לתקן" סביבה

ב-worker context מותקנים שני routes שמגישים מהזיכרון:
- `/index.html` (‏`APP_DOC_RE`) — התרופה המקורית לתקיעת ה-loopback;
- `lang-<code>.json` (‏`LANG_JSON_RE`) — נוספה כשטעינת המילון על-פי-דרישה החזירה את אותה תקיעה.

כללים נגזרים:
1. **כל נקודת-קצה חדשה שהאפליקציה מושכת בעלייה** (קובץ נתונים, מניפסט, וכו') — בדוק אם היא מצריכה
   הרחבה של אותה תרופה. תסמין מובהק: עשרות timeouts בקבצים **לא-קשורים** אחרי שינוי טעינה.
2. ‏**routes פר-בדיקה גוברים** על אלה של ה-worker (‏page-level לפני context-level) — לכן override נקודתי עובד;
   אבל כל `route` שמתקינים בבדיקה **חייב** `unroute` ב-`try/finally`, אחרת הוא דולף לכל הבדיקות
   הבאות באותו worker ומייצר "כשלי רפאים".
3. הפרויקט **service-worker** אינו מקבל את ה-routes האלה — שם הקריאות אמיתיות. בדיקות offline/SW שייכות
   לשם, ויש להתחשב בהבדל במפורש.

## 4. המתנה — תנאי, לעולם לא זמן

- **אסור `waitForTimeout`.** ‏(DoD-11.)
- המתן על תנאי: `waitForFunction`, `expect(locator).toBeVisible()`, או הבטחת-מוכנות שהאפליקציה חושפת
  (למשל `window.__mkLangReady` לאחר טעינת מילון).
- **`waitForResponse` אינו הוכחה שהמצב הוחל** — אירוע הרשת נורה לפני ששרשרת ה-`then` סיימה לעדכן.
  אם אתה בודק תוצאה של פעולה אסינכרונית, המתן על **המצב הנצפה** (DOM/‏getLang()), לא על הבקשה.
  (נתפס בפועל ב-Task 2: בדיקה שנשענה על `waitForResponse` עברה לפעמים גם בלי התיקון.)

## 5. הרצה

`npx playwright test` — **בדיוק כך**. בלי `--retries`, בלי `--workers`, בלי `--grep` כתחליף לריצה מלאה
בשער. ה-config הוא הסמכות (workers מכוילים, `retries: 0`).
- לפני ריצה: ודא ש**אין** שרת ידני על 8123 (הוא מתנגש עם השרת המנוהל של Playwright).
- תן לריצה **להסתיים** — היא מפרקת את השרת שלה בעצמה; אל תהרוג באמצע.
- לכוד קוד יציאה **ישירות**: `npx playwright test; ec=$?` — לעולם לא דרך pipe (‏`| tail` מודד את tail).
- אל תריץ שתי ריצות במקביל, ואל תריץ בזמן שסוכנים כבדים אחרים מתחרים על ה-CPU.
- **כשל, כולל חד-פעמי, הוא באג** — לא מריצים שוב עד ירוק; מאבחנים (‏3-fix rule).

## 6. איכות הבדיקה עצמה

- ‏**RED לפני GREEN**: בדיקה שעברה בריצה הראשונה **בטלה** — כתוב אותה מחדש כך שתיכשל מהסיבה הנכונה.
- טוענים על **אפקט נצפה** — DOM מרונדר, מצב שמור, ערך שצרכן אמיתי קורא. שדה מחושב שאיש אינו קורא
  אינו בדיקה (‏DoD-4/5).
- אימות שפה נעשה ב-**DOM המרונדר**, לא במדד כיסוי ולא ב-grep על החבילה (הלקח מ-v267).
