## 7. ⚠️ שלוש תשובות ששינו את ההנחות — הערכה כנה

הפאנל תמחר את הארכיטקטורה על **שתי הנחות שכעת התבררו כשגויות**, ואני ממליץ נגד React על בסיסן.
**חובה לתקן את התמונה, לא להמשיך בשקט.**

### 7.1 מה השתנה

| התשובה | ההנחה שהפאנל תמחר לפיה | המציאות |
|---|---|---|
| **3.2 — מפתח נוסף: כן** | מחבר אחד → פריימוורק הוא העדפה | **שניים → פונקציות רינדור של 500 שורות הן חומת כניסה** |
| **4.1 — עסק, מספר עובדים על אותם אירועים** | משתמש אחד על N מכשירים → LWW על מסמך, ~5-6 משימות | **עריכה מקבילה רב-משתמשית** — LWW על מסמך **יאבד עבודה של עובד** |
| **4.2 — "הכי מהיר שאפשר"** | polling של שניות → **בלי Durable Objects** | **דחיפה בזמן אמת → DO + WebSocket** |

### 7.2 ההשלכות — ישירות ובלי ריכוך

1. **LWW על מסמך אינו מספיק.** שני עובדים שעורכים את אותו אירוע — האחרון דורס את הראשון.
   נדרש מינימום **LWW ברמת שדה**, ולתרחישים אמיתיים — נעילה או CRDT.
2. **מודל הזהות משתנה מיסודו.** לא "משתמש עם מכשירים" אלא **ארגון עם חברים והרשאות**.
   אירוע שייך ל**ארגון**, לא למשתמש. זה משנה את הסכמה, את ה-auth ואת Paddle (מנוי צוות).
3. **Durable Objects חוזרים לתמונה.** 4.2 + עריכה מקבילה = דחיפה, נוכחות ("מי עורך עכשיו"), ופתרון
   התנגשויות בזמן אמת.
4. **🔴 שאלת בטיחות חדשה:** אם עובד א' משנה טמפרטורה בתוכנית ועובד ב' מבשל לפיה — **מי הסמכות?**
   זה **לא** קיים במודל שלנו כיום, וזה נוגע בשכבת הבטיחות. **צריך הכרעה לפני שסנכרון רב-משתמשי נבנה.**
5. **וזה בדיוק המקום שבו React מצדיק את עצמו.** מצב UI רב-משתמשי בזמן אמת הוא **הטיעון החזק ביותר
   שקיים** לפריימוורק — ועכשיו הוא נכון. יחד עם 3.2 (מפתח נוסף), **שתי ההנחות שעליהן המלצתי נגד
   React התהפכו.**

### 7.3 מה זה **לא** משנה

- **3.1 בעינו:** React אינו השלב הבא. עבודת ההכנה (מודול state, ניווט, חילוץ מודולים) נדרשת
  **בכל מקרה**, ועכשיו **דחוף יותר** — היא מה שיאפשר למפתח השני להיכנס בלי React.
- **הסדר בעינו:** גל 0 → CP2 → ניווט. הסנכרון הרב-משתמשי הוא **פאזה גדולה בפני עצמה**, לא תוספת.
- **3.6 בעינו:** אין חוקים בשרת. גם ברב-משתמשים, הבטיחות נשארת בצד הלקוח ומצוטטת.

### 7.4 המלצתי המעודכנת

1. **להתקדם כמתוכנן** — גל 0 → CP2 → ניווט. **אין שינוי.**
2. **לפצל את הסנכרון לשתי פאזות:**
   **S1 — רב-מכשירי, משתמש אחד** (LWW על מסמך, polling). זה ~5-6 משימות ומספק ערך מיד.
   **S2 — רב-משתמשי לעסק** (ארגונים, הרשאות, LWW פר-שדה או CRDT, DO + WebSocket, נוכחות,
   **וסמכות הבטיחות מ-§7.2.4**). **זו פאזה בסדר גודל של E-programme, לא תוספת ל-S1.**
3. **לפתוח מחדש את שאלת React אחרי S1** — כשהמפתח השני מצטרף ולפני שנבנה את S2. אז שתי ההנחות
   ייבחנו על קוד אמיתי, וזה בדיוק מה שהפיילוט היה אמור לתת — בלי בסיס קוד שני.
